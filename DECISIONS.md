# Aloy design record & history

The living [ARCHITECTURE.md](./ARCHITECTURE.md) is the present-tense reference — *what* Aloy is today. This doc is the record of *why* it got there: decisions with the alternatives weighed, real incidents and their root causes, and the roadmap — including designed-but-unbuilt ideas. Preserved in full so an agent (or developer) can check the reasoning behind any part of the reference, not just a summary.

It grows over time. Land new decisions, incidents, and roadmap updates here; keep ARCHITECTURE.md lean and present-tense.

## Roadmap

### Unified Inbox — built 2026-08-21

**Motivation**: harvested from looking at PostHog's `products/signals` (their background "scout" agents land findings in one searchable Inbox rather than scattered per-feature widgets). Aloy already had the ingredients — Athena is tagged SCOUT, Minerva watches smart-home/reliability, the Vision Timeline and confidence-escalation system both generate discrete findings — but they were siloed: separate sidebar rows, separate dashboard cards, no cross-cutting view.

**Design questions, settled before building** (per the mattpocock-skills/PostHog pattern — these materially changed the shape of the work, worth grilling rather than guessing):
- **Unit of iteration**: collapse by agent, not one row per raw event — matches the Vision Timeline's own existing precedent (bare "NO" descriptions get counted, not shown individually).
- **Lifecycle**: ambient/time-window based (last 24h), no explicit dismissed/resolved state — matches how `connectedClients`/`smartHomeStats` already work, no new persisted state.
- **Cross-agent ranking**: strict recency, no severity scoring — simplest, and avoids inventing a cross-agent severity scale that has no precedent in the codebase.
- **Placement**: new top-level nav entry in the Pantheon list (Sidebar.jsx), styled with Aloy's own brand cyan rather than an agent color, since it isn't itself an agent.

**What feeds it**:
- Apollo (confidence-escalation entries, `claudeEscalations`), Athena (completed research tasks), and Minerva (`securityGuard`/`auditLogger` blocked-access and injection-attempt events) are aggregated server-side in the new `apps/desktop/server/inboxAggregator.cjs` (`getInboxFeed`), exposed both as `GET /api/inbox/feed` and as an Electron IPC channel (`inbox:feed` / `window.electronAPI.getInboxFeed`) mirroring the existing `getSecurityStats`/`getEscalationStats` pattern.
- Vision timeline notable events and lock-unlock history (`lockHistory`) are merged in client-side in the new `InboxView.jsx`, since both are already fetched there (vision directly against Home Assistant, lock history as client-only anomaly-detection state) — pulling them server-side would mean re-implementing HA reachability and shipping client-only state to the backend for no real gain. This also means the Inbox is currently desktop-only; mobile parity is a natural follow-up once the pattern proves out, per the existing precedent of features (TTS/STT/push) shipping to desktop first.
- `smartHomeStats.locksUnlocked` — the half-built, never-rendered signal found in `Sidebar.jsx` earlier this session — still isn't wired into the Inbox directly; the real per-event `lockHistory` array turned out to be the better, already-timestamped source for "a lock was unlocked."

**Bug found and fixed during the build, not before it shipped**: the first version's HTTP-only fetch path silently returned an empty Inbox — no console error, just "Inbox zero." Root cause: the bare-`fetch` fallback path requires a Bearer token read from `localStorage.getItem('aloy_server_auth_token')`, a key that turns out to be **never actually set anywhere in this codebase** (confirmed by grep) — `AthenaWorkspace.jsx`'s identical fallback path has had the same latent, never-triggered bug the whole time, invisible because the real app always has `window.electronAPI` available and takes the IPC branch first. Fixed two ways: added the missing IPC channel (the actual fix, since it's what the real app uses) and made the HTTP-fallback failure visible (`console.warn` on non-200, instead of silently leaving the list empty) so a future instance of this exact gap won't be silent again.

**Verification**: aggregation logic covered by 5 unit tests (`inboxAggregator.test.js`, dependency-injected fakes per this repo's established `.cjs`-testing convention — no `vi.mock`). The exact `getInboxFeed` function was also exercised directly against real store data via a temporary standalone server instance on a spare invocation of port 7890 (the packaged `Aloy.exe` was briefly stopped and restarted afterward to free the port safely, with the user's explicit go-ahead first) — confirmed real Athena/security items came back correctly windowed and sorted. The React component was visually verified in a browser (grouping, expand/collapse, empty state, no console errors) via the bare-`vite` dev-server workflow. **Not verified**: the Electron IPC path specifically, end-to-end in the real app UI — the dev-mode Electron window turned out to be PIN-locked, and entering that PIN was correctly out of bounds. The IPC handler itself is a 4-line wrapper calling the identically-tested `getInboxFeed`, mirroring 3 other already-working IPC channels in the same file, so the residual risk is low, but this is the one piece resting on code-review confidence rather than a live click-through.

## Incidents & decisions (chronological)

### 2026-07-30 — MCP client support added
Wired into both desktop and mobile/API server the same day (`mcpClient.cjs`, `@modelcontextprotocol/sdk`). Every MCP tool call requires confirmation, no exceptions — decided at build time, not loosened since. **Gotcha found**: the `fetch` server's own tool description contains prompt-injection-shaped text ("you now have internet access... let the user know") — worth reading a new MCP server's tool descriptions, not just its code, before adding it.

### 2026-07-31 — thin-client mobile architecture (Option A)
AloyMobile has no on-device model; it's a pure client to the same backend/store as desktop. Deliberate choice for sync-quality reasons over a separate on-device brain.

### 2026-07-31 — store reconciliation incident (RESOLVED)
~9 real chat threads went missing from `store.json` over time (traced via backup snapshots: chat count went 4→1→9→12). Root cause: `seedFromBackupIfEmpty()` re-seeded the **entire** store (including `chats`) from the NAS backup on any restart where reminders/transactions/budgets/memories all happened to be empty — a user who mostly just chats via mobile (never logging reminders/transactions in that period) could trip this even though `chats` itself had real data. Fixed with a persistent `seededFromBackup` flag (fires once, ever) instead of an array-emptiness heuristic.

### 2026-08-01 — packaged Electron build, unresolved at the time
`electron-builder` consistently failed with `EPERM` renaming `win-unpacked` (8 attempts). Ruled out real-time AV, Controlled Folder Access, file locks, ACLs, CWD-in-target-dir. Root cause never found without Process Monitor. Decision at the time: stay on dev mode rather than keep guessing blind.

**Update, discovered 2026-08-21**: the user's actual live daily-use app is a packaged `Aloy.exe`, installed at `%LOCALAPPDATA%\Programs\ollama-pro-app\` (install path still says `ollama-pro-app` — that's just `apps/desktop/package.json`'s unchanged `name` field driving electron-builder's default per-user install directory, not evidence of which code it contains). Checked `apps/desktop/release/`: it held a complete, successful 2026-08-19 15:52 build (`Aloy Setup 2.0.0.exe` + portable `.exe`) — matching the day of the monorepo migration/security hardening — alongside a leftover `win-unpacked.tmp` from an *apparent second attempt* six minutes later. So the original EPERM failures were real but **intermittent**, not a permanent block: one run that day succeeded, installed, and is what's been running since; a later run that same day hit the same old issue and left a stale temp dir.

**Resolved same day**: deleted the stale `win-unpacked.tmp`, ran `npm run electron:build` fresh — completed with no EPERM error at all. Quit the live `Aloy.exe` (with the user's explicit go-ahead), ran the new `Aloy Setup 2.0.0.exe` installer (one-click NSIS, auto-relaunches on completion), and verified live: `GET /api/inbox/feed` against the freshly-installed app returned real data including both queued Hephaestus/Council items, confirming today's full set of fixes (Inbox, PersonaModal/CameraModal exit animation, Sidebar stat-pop, both Hephaestus review-gate fixes) are now actually running in daily use, not just verified in source. The pipeline itself was never structurally broken — worth a normal `electron:build` run after future changes rather than assuming it'll fail; if EPERM recurs, retry once before escalating to a deeper investigation, given it didn't reproduce on the very next attempt here.

### 2026-08-03 — confidence escalation: two real calibration lessons
1. **Binary YES/NO self-judgment discriminates; 3-way HIGH/MEDIUM/LOW does not.** The local model picked "MEDIUM" >90% of the time regardless of actual correctness when asked to self-rate three ways — a degenerate safe-middle answer that shipped as v1 and looked fine in isolated testing. Reframed as "Is this answer fully correct and complete? YES or NO" against the same test cases, it correctly flagged real errors.
2. **The check cannot block the visible answer.** Awaiting it before showing anything added a hidden 3-20s delay to every turn. Decision (with the tradeoff made explicit to the user): show the local answer instantly, append a correction later if the background check warrants it.

Also fixed same day: confidence escalation was firing on tool-call-driven completions (Claude has no way to verify a real-world action happened, and was giving generically wrong "I can't control your smart home" answers on turns where Aloy actually could and did) — added a `followedToolCall`/`usedTools` flag through both desktop and mobile/server turn paths to skip the check when a completion followed a tool call.

### 2026-08-03 — kitchen light false-success bug (real production bug, user-reported)
Aloy said "I've turned it on," the light never turned on. Root cause: `control_smart_home_device`'s own tool description used `light.kitchen` as an example entity_id, the model pattern-matched off the example instead of the real entity (`light.kitchen_main_lights`), and Home Assistant's service-call endpoint returns HTTP 200 even for a nonexistent entity_id (silent no-op). Two-part fix: removed the misleading example from the tool description; added entity-existence validation before calling the service, returning a clear failure + "did you mean" list instead of a false success.

### 2026-08-03 — mic hang, two independent root causes (RESOLVED)
1. A genuine Werkzeug dev-server bug: one specific real recorded `.webm` hung with zero diagnostic output below the WSGI layer. Fixed by switching `whisper_server.py`'s entrypoint to `waitress`, a real production WSGI server.
2. A CUDA DLL loading issue specific to restarting under a different interpreter: `os.add_dll_directory()` alone isn't enough for ctranslate2's compiled loader to find `cublas64_12.dll`; also needed prepending the nvidia package `bin` dirs to `PATH` directly.

### 2026-08-19 — Hephaestus/Cauldron security hardening
All identified gaps in the self-modifying-code pipeline fixed (5 commits) around the same time the repo moved to the unified `aloy` monorepo.

### 2026-08-19/20 — v2.0.0: unify desktop & mobile ecosystem
Repo restructured from two separate directories (`ollama-pro-app`, `AloyMobile`) into the `apps/desktop` + `apps/mobile` monorepo. The Pantheon naming (Hephaestus/Athena/Apollo/Minerva/Hermes/Pantheon Council) was introduced as product framing over existing and new server modules around this release.

### Standing policy — don't bolt reviewers onto Hephaestus without flagging injection exposure first
Any proposal to add new automated review/critique layers onto Hephaestus's autonomous coding pipeline needs the injection-exposure discussion surfaced explicitly before building, not after. (Confirmed relevant again 2026-08-21 when reviewing PostHog's ReviewHog product, which has its own mature answer to this — fork-PR refusal, a hard per-run budget, a "mechanical fix vs. design decision" bar — worth reading as reference before any future Hephaestus autonomy work, not something to wire in casually.)

### 2026-08-21 — audited all 24 Hephaestus work orders, found and fixed two real gaps

Requested review of `~/.aloy-server/hephaestus-tasks.json` (24 total: 19 deployed, 3 auto-closed, 2 queued at the time).

**Gap 1 — Pantheon Council-dispatched work orders silently stall and loop forever.** The 2 queued items ("Sidecar Auto-Recovery", "Bundle Pruning") were each the *third* occurrence of the same directive — the prior two rounds weren't human-rejected, they were auto-closed by `hephaestus.cjs`'s `STALE_QUEUED_MS` (24h) sweep: `"Auto-closed: work order sat unstarted past the staleness window and was never picked up."` Root cause: `createTask` only creates task *data* — actually generating a diff and calling `/api/hephaestus/tasks/:id/stage` is a human-driven Cauldron UI step with no automatic trigger. A Council-dispatched directive is invisible until you happen to open the Cauldron within 24h of it being created, so it silently expires and gets recreated the following convene with slightly wider scope, indefinitely. `conclave.cjs` already had a code comment documenting this exact pattern occurring before, with a dedup guard added — but that guard only stops the Council from creating a *second* copy while one is already open; it doesn't address why the first copy never gets picked up.

**Deliberately not fixed**: making Hephaestus auto-generate and auto-stage diffs for Council directives with no human specifying content — that's a materially different, much higher-risk feature (an LLM given open-ended write access to invent its own code changes), and squarely the kind of thing the standing injection-exposure policy above says to flag before building, not fold in as a side effect of a "fix the stuck queue" ask.

**Fix actually made**: surfaced queued, Council-requested (`requestedBy === 'pantheon_conclave'`) work orders in the new Inbox (`inboxAggregator.cjs`) as a Hephaestus-agent item, shown unconditionally (not gated by the 24h window) since "still queued" is itself the thing needing attention. This closes the actual gap — invisibility — without expanding Hephaestus's autonomy.

**Gap 2 — the review gate's own adversarial test proved it doesn't block dangerous code, and tracing current code, that gap was still live.** A 2026-08-16 task (`requestedBy: operator_eval`, targeting the pre-monorepo `ollama-pro-app` path) deliberately staged `return eval(userInput);` into `store.cjs`. The local heuristic reviewer correctly flagged it (`[SECURITY FLAG] Potentially unsafe dynamic execution`) but scored it 60/100 → `NEEDS_REVISION`, which — unlike a detected prompt-injection attempt, which forces `REJECTED` regardless of score — does **not** block deployment, only a human declining to approve does. It was approved (~2h later, consistent with a human clicking through, not a script) and deployed. Confirmed the literal injected code isn't in the current codebase (the target file's whole directory is gone, superseded by the monorepo), but traced the current reviewer logic and found the structural gap unchanged: `DANGEROUS_EXECUTION_PATTERNS` matches only cost score points in `reviewWithLocalHeuristic`, and the same patterns weren't checked at all against the Claude/Gemini review path — that path relied entirely on the LLM noticing and self-reporting eval()-shaped code in its own verdict, with no independent backstop the way injection detection already had one.

**Fix**: `hephReviewer.cjs`'s `reviewWithLocalHeuristic` now forces `REJECTED` on any `DANGEROUS_EXECUTION_PATTERNS` match, same as injection-shaped text. Added `scanForDangerousExecution()`, an independent regex scan applied at the `hephaestus.cjs` call site to *every* review result (heuristic, Claude, or Gemini) — mirroring the existing `injectionAttemptDetected` force-override — so the backstop no longer depends on which reviewer ran or on the LLM catching it itself. Covered by `hephReviewer.test.js`, including a regression test reproducing the exact 60/100-NEEDS_REVISION scenario from the 2026-08-16 finding and asserting it now forces `REJECTED`. `autoDeploy` still defaults to `false` everywhere (including Council-dispatched tasks) — nothing currently ships without an explicit human Approve click regardless of this fix, so the practical exposure was "a flagged diff could be approved past its own flag," not "ships with zero human in the loop." Not yet verified against the real packaged app specifically (see the "packaged Electron build" entry above — the live `Aloy.exe` runs pre-monorepo code and would need a rebuild to pick this up either way); verified via unit tests (`hephReviewer.test.js`, `inboxAggregator.test.js`) and `node --check` syntax validation on every touched file.

### 2026-08-21 — modal exit-animation bug (desktop), fixed
`PersonaModal.jsx` and `CameraModal.jsx` had `if (!isOpen) return null` sitting *before* `return <AnimatePresence>` — this unmounts the whole subtree, AnimatePresence included, synchronously, skipping the exit animation entirely. Open played its spring nicely; close snapped instantly. Fixed by moving the guard to `{isOpen && (...)}` *inside* AnimatePresence, matching the already-correct pattern in `FinancesPanel.jsx`.

### 2026-08-21 — mobile drawer: timing → spring, then a real regression, then fixed
Changed the Threads drawer from `Animated.timing` (flat 220ms/200ms ease) to `Animated.spring` to match desktop's spring feel — verified live on both the emulator and the physical phone (mid-close screenshots showing genuine sliding motion, not a snap).

User then caught a real regression live: the dark backdrop stayed visible 1-2 seconds *after* the drawer had visually finished closing. Root cause: RN's `Animated.spring` default rest-detection thresholds (`restSpeedThreshold`/`restDisplacementThreshold`, both `0.001`) are tight enough that the spring keeps making imperceptible residual oscillations for a second or two after it looks done, and the backdrop's removal is gated on that same `.start(callback)` firing. Fixed by loosening both thresholds to `5` — visually indistinguishable motion, but the completion callback now fires as soon as the motion is actually imperceptible. Verified by timestamped rapid-fire screenshots: backdrop fully cleared by ~0.6s post-tap after the fix, down from 1-2s. **General lesson**: any time a spring's completion callback gates something visible, check the rest thresholds explicitly — RN's defaults optimize for numerical precision, not perceptual completion.

### 2026-08-23 — coder model switched 14b → 7b, and a real drift bug fixed along the way

Prompted by `llmfit` (harvested from AlexsJones/llmfit — see the repo-harvest conversation) scoring `qwen2.5-coder:14b` as only "Good" fit on this machine's RTX 4070 SUPER (12GB VRAM, shared with Whisper STT) vs. "Perfect" fit for the 7b variant at comparable-or-better speed. Changed the default in `models.cjs` (the actual single source of truth, with its own header comment explaining it exists specifically to prevent model-ID drift across files).

While making the change, found `modelRouter.cjs` had its own independent hardcoded `MODEL_REGISTRY` with the *exact* '14b' string models.cjs's header warns about — never migrated to read from the single source of truth. Fixed by having it import `MODELS` from `models.cjs` instead. Also found a third hardcoded copy in `aloyServer.cjs`'s VRAM-purge endpoint's secondary-models list; same fix. Verified: a real (non-mocked) Ollama call against `qwen2.5-coder:7b` returns a correct response, and `routeModelRequest()` now selects it for a coding-keyword prompt.

**Aside, unrelated to the model swap**: `server/skillsDashboard.test.js` and `server/conclave.test.js` intermittently time out (5s) in this environment — confirmed NOT caused by the model change (reverted to 14b, still failed; re-tested at 7b, passed on a later run) — looks like environmental Ollama-latency flakiness in already-uncommitted WIP code predating this session, not a regression to chase down here.

### 2026-08-23 — added workout tracking (harvested from norrdev/OpenGym), and found a real silent-persistence bug along the way

Built the scoped v1 from the OpenGym harvest conversation: a `workouts` store domain (`{id, date, exercises: [{name, sets, reps, weight}], notes}`, deliberately not OpenGym's full program-builder/exercise-catalog/muscle-mapping system), `log_workout`/`get_workout_history` chat tools (available on both desktop and mobile/API, since both share `src/services/tools.js`), a `GET /api/workouts` route, and a new "🏋️ Fitness" tab in Hermes's `SubAgentsHub.jsx` (streak counter, quick-log form, delete). New `src/services/workouts.js` holds the pure logic (`createWorkoutEntry`, `calculateWorkoutStreak`, `formatWorkoutHistoryContext`).

**Real bug found while wiring the new tab's persistence**: `SubAgentsHub.jsx` had `window.electronAPI?.storeSet(...)` in five places (memories ×2, userProfile, reminders ×2) — `storeSet` does not exist in `preload.cjs` (only `storeSave` does), so the optional-chaining guard silently skipped persistence every time, while local state still updated and a "saved" toast still fired. Editing memories/profile/reminders from this specific tab has been a no-op that *looked* successful since whenever this code landed — gone until the app restarts and the shared store reloads from disk. Fixed all five call sites to `storeSave`. Not otherwise investigated (e.g. whether other UI surfaces like `MemoryModal.jsx` also write these domains correctly, which would explain why this wasn't noticed).

**Verification note**: the bare-`vite` dev tab used for UI verification became persistently unresponsive to CDP `Page.captureScreenshot` (30s timeouts) partway through this check, while JS execution and DOM state remained fully queryable — confirmed via direct DOM inspection (not screenshots) that the Fitness tab renders correctly, the log-workout form works end-to-end (submitted a real entry, streak correctly updated to "1 day streak"), and the tab was not actually blank as the failed screenshots misleadingly suggested. Root cause of the screenshot flakiness not identified — likely specific to that long-lived tab's accumulated state after many hours in this session, not a code issue. Delete was not independently confirmed (a DOM-query miss, not a functional failure) — it shares the exact same `setWorkouts`/`storeSave` path already proven to work for add.

### 2026-08-24 — Fitness tab: surfaced scheduled workouts from Google Calendar

Added a "📅 Upcoming from your calendar" section to the Fitness tab, reusing the existing `fetchGoogleCalendarEvents` (already used by `DashboardView.jsx`'s "Upcoming Schedule" card, self-fetched the same way here rather than prop-drilled from `App.jsx`). Keyword-matched against event summaries (`isWorkoutEvent`/`filterWorkoutCalendarEvents` in `workouts.js`) rather than requiring a dedicated calendar/category — matches whatever the user already names their gym/training events. Deliberately kept separate from the logged-workout streak: a calendar block is *planned*, not *done*, so it doesn't feed `calculateWorkoutStreak`.

**Real false-positive found against live calendar data**: The user has recurring "Meal 3: Pre-Workout Snack" reminders — `"workout"` is a literal substring of `"Pre-Workout"`, so the naive keyword match caught meal-prep reminders as workouts. Fixed with a `NON_WORKOUT_KEYWORDS` exclusion list (`meal`, `snack`) checked first, before the positive keyword match. Verified against the real live calendar both before and after the fix (confirmed the false positives disappeared while the genuine "Workout: Push Day (Chest) + 5-Mile Ride"-style entries stayed).

**Unrelated mistake worth recording**: while trying to inspect `.env` for the Home Assistant base URL to verify this via a direct curl, a `sed` redaction pattern failed and printed the real `VITE_HA_TOKEN` JWT value in full into a tool result. Low real risk (a local-only HA long-lived access token, not a cloud credential), but the lesson holds regardless: never construct an ad hoc regex to redact a secret before printing it — read the specific key you need with a method that never echoes the value, or avoid touching `.env` contents directly at all when a safer path (like verifying through the app's own code path in a browser) exists.

### 2026-08-24 — Fitness tab, round 2: calendar events had exercise detail in `description`, but the UI only showed `summary`

Shipped the round-1 calendar section, rebuilt, reinstalled — The user reported "I see the workouts but it doesn't include the workouts," which turned out to mean the exercise detail (sets/reps/weight) was missing, not the events themselves. Checked live: `fetchGoogleCalendarEvents` only ever captured `summary`/`start`, never `description` — and actual calendar events (e.g. "Workout: Push Day (Chest) + 5-Mile Ride") carry a full per-exercise breakdown in the description field ("- Smith Machine Flat Press: 3 sets x 8-10 reps", etc.) that was simply never fetched.

Fixed by adding `description: ev.description || ''` to the shared `fetchGoogleCalendarEvents` mapping (additive, non-breaking for existing consumers like `DashboardView.jsx`'s schedule card) and making each calendar-workout row in the Fitness tab expandable (click to reveal the full description, `white-space: pre-line` to preserve the calendar author's line breaks/bullets). Verified against the real live calendar: expanding "Push Day (Chest) + 5-Mile Ride" shows all 6 logged exercises with their real sets/reps.

### 2026-08-24 — Athena stuck-in-`queued` tasks surfaced in the Inbox

An audit of every Pantheon sub-agent was run to confirm they're actually completing their work, not just running. Checked `athena-tasks.json` directly: 24 tasks total, and one — a user-requested research query on local SLM inference on Nvidia GPUs — had been sitting in `queued` for 5 days. Traced why: `AthenaEngine.createTask` schedules `executeTask` via `setImmediate`, so a healthy task moves out of `queued` within the same tick; `recoverStaleTasks()`'s constructor-run sweep only recognizes `researching`/`synthesizing` as orphanable states, never `queued` — so a task whose process died in that exact `setImmediate` window is invisible to every existing recovery mechanism and sits forever with nothing to retry it.

Scoped this to the same fix already shipped for Hephaestus's queued Council work orders (see above): surface it ambiently in the Inbox rather than attempting an actual resume/retry mechanism, which was explicitly deferred as a separate, bigger undertaking (checkpointing Athena's research pipeline across restarts). Added a `stuck-research-task` block to `inboxAggregator.cjs` (unconditional, not window-gated, same ambient-alert shape as the Hephaestus and Minerva lock-unlock items) and a `'stuck-research-task': 'Never started'` label in `InboxView.jsx`. Added a dedicated test in `inboxAggregator.test.js` covering queued vs. researching vs. completed tasks. Full suite: 220/220 passing. Verified against real live data via a one-off Node script against the actual `athenaEngine`/`globalHephaestus`/`globalMinerva` instances: 14 total Inbox items, exactly 1 `stuck-research-task`, matching the real 5-day-old queued task.

### 2026-08-26 — Kokoro sidecar auto-revival & Minerva mobile health status calibration (RESOLVED)

**Incident 1: Kokoro TTS reported offline on Desktop and Mobile**
- **Root Cause**: The standalone Kokoro neural voice server (`~/.aloy-server/services/kokoro_server.py` on port 8888) was stopped after a host reboot/gaming session and had no automatic resurrection logic in the backend watchdog daemon.
- **Fix**: Added `ensureKokoroProcessRunning()` in `apps/desktop/server/sidecarWatchdog.cjs` to auto-spawn `kokoro_server.py` using `openwebui_env/Scripts/python.exe` in background mode when watchdog detects port 8888 offline on `GET /voices`.
- **Verification**: Verified endpoint `http://127.0.0.1:8888/voices` responds with authenticated Bearer token and returns all 7 studio neural voices.

**Incident 2: Aloy Mobile showed valid API keys and cloud models in red**
- **Root Cause**: In `apps/mobile/App.tsx`, the `minervaHealth.dependencies` status badge styling checked only `v.status === 'online' || v.status === 'mounted'`.
